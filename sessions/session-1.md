## Размышления

- Задача — не разработка, а планирование QA-сессии над уже готовым
  чужим прототипом (сессия разработки закрыта). Использовал скилл
  `superpowers:brainstorming`, но не по «архитектурному» пути (нет
  approaches/design doc в `docs/`) — адаптировал под спецификацию
  QA-сессии с записью прямо в существующий `SPEC.md`, как явно попросил
  пользователь.
- Первая ошибка с моей стороны: после ответа пользователя про «глубокое
  тестирование в два шага» я сразу выполнил шаг 1 (чек-листы) вместо
  того, чтобы сначала зафиксировать ответ в спецификации и продолжить
  вопросы. Пользователь поправил — чек-листы были преждевременны для
  этой стадии, хоть и не бесполезны (сохранил их содержание в контексте
  для последующей сборки тест-плана). Урок: разделение «спецификация»
  vs «работа по спецификации» нужно соблюдать строго, даже когда ответ
  пользователя выглядит как готовность перейти к деталям.
  Заказчик сам разрешил не выбрасывать чек-листы, а просто перенести их
  использование на нужный шаг — так и сделал при сборке тест-плана
  этой же сессией.
- Несколько раз пользователь передумывал/поправлялся на уже отвеченных
  вопросах (кроссбраузерность: сначала вариант A, затем сразу
  «извините, вариант B»). Это ожидаемая часть диалога, не ошибка модели
  — зафиксировал финальный выбор без переспрашивания заново.
  Аналогично: план настроить Playwright MCP для кроссбраузерности был
  явно назван пользователем как задел на будущее, а не требование
  текущей сессии — не стал предлагать установку сейчас, как и требует
  AGENTS.md («новый инструмент — только с вопросом»).
- Важная предметная поправка от пользователя: изначально сформулировал
  пункт про «сортировку истории при равном timestamp» как открытый
  вопрос. Пользователь указал, что это неверно — `renderHistory` не
  сортирует, а разворачивает массив (`.slice().reverse()`), то есть
  порядок детерминирован кодом, а не оставлен на усмотрение заказчика.
  Разница существенная: «открытый вопрос» подразумевает решение,
  которое требует ответа человека, а «верифицируемое поведение» — то,
  что просто нужно подтвердить фактом на проверке. Перенёс пункт из
  раздела «Открытые вопросы» в «Сценарии» (зона 4) как пункт на
  верификацию.
- При чтении кода для чек-листов обнаружил вероятную уязвимость:
  значения полей формы (имя/адрес/телефон/комментарий) подставляются в
  `innerHTML` экрана подтверждения без экранирования — потенциальный
  XSS. Явно спросил пользователя, включать ли это в объём тестирования
  (это не было частью исходной постановки от него) — подтвердил,
  включили отдельным пунктом. Решение не принимал за него: находка при
  чтении кода — повод спросить, а не тихо добавить в план.
- Accessibility исключили из объёма явно, с зафиксированной причиной
  пользователя (сквозное измерение поверх выбранных зон, не требуется
  заданием, нет чистого кластера в таксономии багов) — записано в
  «Чего не делаем» `SPEC.md`, а не просто опущено молча.
- Кроссбраузерность в итоге сузили до одного движка (Chrome через
  `claude-in-chrome`), так как для второго движка (Safari/Firefox) в
  этой сессии нет автоматизации, а устанавливать новый инструмент
  (Playwright) без отдельного вопроса запрещено правилами проекта.
- Тест-план собрал из содержимого чек-листов (сохранённых в этом же
  разговоре), с перевесом на зоны 1 (валидация формы) и 4 (история/
  localStorage) — они дали больше всего пограничных и негативных
  случаев при анализе кода. Явно спросил про имена файлов для
  артефактов (`test-plan.md`, `bug-reports.md`, `qa-notes.md`) вместо
  того, чтобы придумывать расположение самому — в `AGENTS.md` формат
  файлов для QA-деливерablesов не был зафиксирован явно.
- `bug-reports.md` пока не создан намеренно — в проекте (и в
  AGENTS.md) формат баг-репорта уже полностью описан; создавать пустой
  файл-заготовку сейчас означало бы боилерплейт «на будущее». Создам
  его вместе с первым реальным найденным багом.
- Выполняя п. 10 тест-плана (граница слота доставки), изначально план
  предполагал «выставить системное время». Отказался от этого сам, без
  вопроса пользователю — смена системных часов ОС подпадает под
  запрещённую категорию действий («изменение системных настроек»), а
  `generateDeliverySlots` и так принимает `now` параметром, так что
  вызов с явно сконструированным `Date` через `node` даёт тот же
  результат без риска и без легитимной причины трогать ОС.
- При тестировании XSS (п. 3) не стал использовать классический
  `alert(1)` — во всех использованных инструкциях по `claude-in-chrome`
  прямо сказано не триггерить JS-диалоги, они блокируют дальнейшие
  команды сессии. Заменил на `console.error('XSS-TRIGGERED-...')` с
  уникальной меткой и подтвердил выполнение через
  `read_console_messages` — тот же факт (произвольный код выполняется),
  без риска зависания сессии.
- Баги 5 и 6 из тест-плана (невалидный JSON и валидный JSON без поля
  `items`) объединил в один баг-репорт (**Баг 2**) с двумя вариантами
  воспроизведения, а не завёл как два отдельных. Причина: у обоих один
  и тот же корень — `loadOrders`/`renderHistory` не проверяют форму
  данных перед использованием. Заводить это как два разных бага
  выглядело бы попыткой накрутить число находок вместо честного отчёта.
- Наткнулся на техническое ограничение: `resize_window` через
  `claude-in-chrome` не даёт окну стать уже 606px в этой среде (пробовал
  768/375/320 — везде фактические `window.innerWidth` = 606). Прежде
  чем сдаваться, явно сообщил пользователю проблему с тремя вариантами
  выхода, не стал тихо считать пункт 12 «пройденным» на 606px вместо
  честных 375px. Пользователь отверг вариант с DevTools-автоматизацией
  (риск нестабильности ради одного пункта) и предложил протестировать
  дешёвый трюк — CSS `zoom: 200%` на `<html>`, из расчёта, что это
  математически сожмёт эффективный viewport. Проверил гипотезу через
  `matchMedia('(max-width: 420px)').matches` — результат `false` даже
  при zoom 200%: медиа-запросы Chrome считаются от физического
  viewport, а не от CSS zoom, идея не сработала на практике, не только
  в теории. Перешли к плану Б, но не как к «не проверено», а с честной
  границей: 606/768px — подтверждено скриншотами, <420px — подтверждено
  только чтением синтаксически верного CSS-правила, без подтверждения
  реального рендера.
- Пункт про повторную проверку после фикса бага (критерий приёмки в
  `SPEC.md`) в этой сессии закрыть нельзя в принципе — правки кода при
  QA запрещены `AGENTS.md`, а без правки нечего перепроверять. Этот
  критерий остаётся открытым до отдельной будущей сессии, где кто-то
  (не QA-агент) исправит хотя бы один из найденных багов.
