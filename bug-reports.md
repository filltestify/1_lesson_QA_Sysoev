## Баг 1

**Заголовок:** Поле «Имя» на экране оформления заказа не экранируется —
HTML/JS-инъекция на экране подтверждения

**Severity:** Критично

**Предусловие:** сервер поднят (`http://localhost:8765/`), в корзине
есть товар, открыт экран «Оформление заказа»

**Шаги воспроизведения:**
1. В поле «Имя» ввести `<img src=x onerror="console.error('XSS-TRIGGERED-9f3a')">`
2. В поле «Адрес доставки» и «Телефон» ввести любые валидные значения
   (например, `ул. Ленина, д. 1` и `12345`)
3. Нажать «Подтвердить заказ»

**Ожидаемый результат:** значение поля «Имя» выводится на экране
подтверждения как обычный текст, без интерпретации как HTML

**Фактический результат:** значение подставляется в `innerHTML`
(`app.js`, `renderConfirmation`) без экранирования; тег `<img>`
рендерится как настоящий элемент, обработчик `onerror` выполняется —
в консоли браузера появляется `[ERROR] XSS-TRIGGERED-9f3a`. Это
подтверждённое выполнение произвольного кода через данные формы, не
гипотеза

**Окружение:**
- Версия приложения: без git, дата проверки 2026-08-16
- Операционная система: macOS (Darwin 25.5.0)
- Браузер: Chrome 151.0.0.0
- Мобильное устройство: не применимо

**Дополнительная информация:** тот же путь (без экранирования) используется
для полей «Адрес», «Телефон» и «Комментарий» — не проверялись отдельно,
но в коде идентичны по обработке

**Вложения:** `screenshots/bug1-xss-confirmation.png` — сломанная
иконка `<img>` на экране подтверждения вместо текста имени

**Кластер:** Функционал/Логика

## Баг 2

**Заголовок:** Некорректные данные в `localStorage["orders"]` роняют
переход на экран «Мои заказы» необработанным исключением

**Severity:** Критично

**Предусловие:** сервер поднят, открыто приложение на любом экране

**Шаги воспроизведения (вариант А — невалидный JSON):**
1. В консоли браузера выполнить
   `localStorage.setItem('orders', '{this is not valid json!!!')`
2. Нажать «Мои заказы» в шапке

**Шаги воспроизведения (вариант Б — валидный JSON без поля `items`):**
1. В консоли выполнить
   `localStorage.setItem('orders', JSON.stringify([{id:'order-broken-1', name:'Тест', address:'Адрес', phone:'123', total:500, timestamp: Date.now()}]))`
2. Нажать «Мои заказы» в шапке

**Ожидаемый результат:** экран «Мои заказы» открывается; при
невозможности прочитать данные — показывается дружелюбное сообщение
(например, «Не удалось загрузить историю») либо пустое состояние, а не
падение

**Фактический результат:** кнопка «Мои заказы» визуально становится
активной, но содержимое экрана не меняется — остаётся то, что было
показано до клика. `loadOrders()` бросает необработанное исключение
(`JSON.parse` — вариант А, `orderItemsHtml` на `undefined.map` —
вариант Б), которое прерывает выполнение `renderHistory()` до вызова
`showScreen('history')`

**Окружение:**

- Операционная система: macOS (Darwin 25.5.0)
- Браузер: Chrome 151.0.0.0
- Мобильное устройство: не применимо

**Дополнительная информация:**

```
    at JSON.parse (<anonymous>)
    at loadOrders (app.js:120:21)
    at renderHistory (app.js:144:18)
    at HTMLButtonElement.<anonymous> (app.js:215:5)

[EXCEPTION] TypeError: Cannot read properties of undefined (reading 'map')
    at orderItemsHtml (app.js:124:16)
```

**Вложения:** `screenshots/bug2-history-corrupted-localstorage.jpg` —

активной)

**Кластер:** Обработка ошибок, алертов и уведомлений

**Доп. проверка независимым аудитом (сессия 2):** протестирован третий
вариант порчи данных — `localStorage.setItem('orders', 'null')`
(синтаксически валидный JSON, но не массив) — тоже падает:
`TypeError: Cannot read properties of null (reading 'length')` в
`renderHistory`. Это подтверждает, а не опровергает решение объединить

один и тот же корень — `loadOrders`/`renderHistory` не проверяют форму
данных перед использованием, значит и правится одним фиксом.

```js
const actual = { heading, historyScreenHidden };
const passed = actual.heading === expected.heading

```

## Баг 3

**Заголовок:** Отправка формы оформления с опустошённой (через панель
корзины) корзиной молча возвращает в меню и теряет введённые данные

**Severity:** Не критично

**Предусловие:** сервер поднят, в корзине есть товар, открыт экран
«Оформление заказа», форма заполнена валидными данными

**Шаги воспроизведения:**
1. На экране «Оформление заказа» заполнить все поля валидно
2. Открыть панель корзины (кнопка «Корзина» в шапке — доступна и на
   этом экране)
3. Удалить единственный товар из корзины (кнопка «✕»)
4. Закрыть панель корзины, оставаясь на экране оформления
5. Нажать «Подтвердить заказ»

**Ожидаемый результат:** пользователь получает понятное сообщение,
что корзина пуста и заказ не может быть оформлен (либо кнопка
«Подтвердить заказ» блокируется при опустошённой корзине, как уже
блокируется кнопка «Оформить заказ» в самой панели)

**Фактический результат:** `handleCheckoutSubmit` (`app.js`, строка
168) при `cart.length === 0` тихо вызывает `showScreen('menu')` без
какого-либо сообщения — пользователь не понимает, почему заказ не
оформился. Заказ в `localStorage` не создаётся (подтверждено —
количество заказов до и после действия не изменилось)

**Окружение:**
- Версия приложения: без git, дата проверки 2026-08-16
- Операционная система: macOS (Darwin 25.5.0)
- Браузер: Chrome 151.0.0.0
- Мобильное устройство: не применимо

**Дополнительная информация:** Исправлено по итогам независимого
аудита (сессия 2): в первой версии этого репорта было написано, что
введённые имя/адрес/телефон «нигде не сохраняются и теряются без
предупреждения» — это неточность. Поля формы (`field-name` и т.д.) на
самом деле не очищаются, так как экран просто скрывается атрибутом
`hidden`, а не перерендеривается заново — значение никуда не пропадает,
оно остаётся в DOM и будет видно при следующем визите на этот экран.
Реальная проблема этого бага — только отсутствие сообщения о причине
молчаливого редиректа. Судьба самих введённых данных (что с ними
происходит дальше) — отдельный **Баг 4**, не часть этого репорта.

**Вложения:** `screenshots/bug3-empty-cart-silent-redirect.jpg` —
экран после нажатия «Подтвердить заказ» с пустой корзиной (открылся
экран меню вместо ошибки)

**Кластер:** UX

## Баг 4

**Заголовок:** Данные формы оформления (имя/адрес/телефон/комментарий)
не очищаются между визитами на экран — риск отправить новый заказ со
старыми чужими данными

**Severity:** Критично

**Предусловие:** сервер поднят, ранее уже был успешно оформлен хотя бы
один заказ (форма была заполнена и отправлена)

**Шаги воспроизведения:**
1. Добавить товар А в корзину, оформить заказ на имя «Алексей Старый»,
   адрес «ул. Старая, д. 1», телефон `+79990000001` — заказ успешно
   оформлен
2. Вернуться в меню, добавить в корзину другой товар Б (для другого
   получателя/повода)
3. Открыть панель корзины → «Оформить заказ»

**Ожидаемый результат:** поля «Имя», «Адрес доставки», «Телефон»,
«Комментарий» на новом заходе пустые — форма не должна предполагать,
что новый заказ идёт по адресу предыдущего

**Фактический результат:** все поля предзаполнены значениями из
предыдущего заказа («Алексей Старый», «ул. Старая, д. 1»,
`+79990000001`) — ничего не очищается ни при успешной отправке, ни при
последующих визитах на экран. Если пользователь не заметит и сразу
нажмёт «Подтвердить заказ», новый заказ реально уйдёт со старыми
данными. Это не гипотетический риск: при живой проверке я (в роли
тестировщика) дважды подряд случайно отправил именно так — два новых
товара («Пепперони», «Том-ям») действительно оформились на «Алексея
Старого» и старый адрес, хотя предполагался ввод новых данных

**Окружение:**
- Версия приложения: без git, дата проверки 2026-08-16
- Операционная система: macOS (Darwin 25.5.0)
- Браузер: Chrome 151.0.0.0
- Мобильное устройство: не применимо

**Дополнительная информация:** найдено при перепроверке Бага 3 в ходе
независимого аудита (сессия 2) — аудит указал, что поля не очищаются;
живая проверка показала, что это не нейтральный факт, а отдельный риск
с более высокой серьёзностью, чем у Бага 3

**Вложения:** `screenshots/bug4-stale-form-data.png` — поля формы

## Повторная проверка после фикса (сессия 6, 2026-08-16)

Код обновлён вне QA-роли (не мной). Заявлено три исправления:
1. Экранирование `name`/`address`/`phone`/`comment` в
   `renderConfirmation` (`escapeHtml` в `logic.js`).
2. `checkout-form.reset()` + очистка текстов ошибок после успешного
   заказа (`resetCheckoutForm()` в `app.js`).
3. `loadOrders()` не падает на некорректных данных — новая функция
   `parseOrders()` в `logic.js`, оборачивает `JSON.parse` в try/catch и
   проверяет `Array.isArray`.

Перепроверено тем же способом, что и при первом обнаружении (то же
приложение, тот же `claude-in-chrome`, доказательства — скриншот/
консоль), не на слово.

**Методологическая находка по пути:** первая попытка перепроверки Бага 1
дала ложноотрицательный результат — на странице снова была видна
сломанная иконка `<img>`. Причина не в коде: браузер отдавал `app.js`
из HTTP-кэша, где лежала версия до фикса (`curl` к серверу напрямую
показал, что сервер уже отдаёт исправленный файл). После жёсткой
перезагрузки (`Cmd+Shift+R`) результат изменился на корректный. Вывод:
после любого обновления кода в этом стенде обязательна перезагрузка
без кэша перед проверкой — иначе легко зафиксировать «не почини­лось»
там, где на самом деле проблема в кэше браузера.

### Баг 1 (XSS) — статус: **закрыт**

Повторил исходные шаги: имя —
`<img src=x onerror="console.error('XSS-RETEST-fix1b')">`, адрес и
телефон валидны. После жёсткой перезагрузки страницы (см. находку
выше) на экране подтверждения тег отобразился как обычный текст
(`&lt;img src=x onerror=...&gt;`, видно как символы, не как элемент),
консоль осталась чистой — `console.error` не выполнился. Проверено
через `document.getElementById('confirmation-details').innerHTML`:
значение содержит `&lt;img ...&gt;` в экранированном виде.
Доказательство: `screenshots/retest-bug1-xss-escaped.png`.

### Баг 4 (старые данные формы) — статус: **закрыт**

Оформил заказ на «Алексей Старый» / «ул. Старая, д. 1» /
`+79990000001` (успешно). Добавил другой товар, снова открыл
«Оформление заказа» — все поля («Имя», «Адрес доставки», «Телефон»,
«Комментарий») пустые, старые данные не подставляются. Доказательство:
`screenshots/retest-bug4-form-cleared.jpg`.

### Баг 2 (падение на некорректном `localStorage`) — статус: **закрыт частично**

- **Вариант А (невалидный JSON)** — закрыт. Записал в
  `localStorage["orders"]` заведомо не-JSON строку, открыл «Мои
  заказы» — экран корректно показывает «Заказов пока нет.» вместо
  падения. Доказательство: `screenshots/retest-bug2-variantA-fixed.jpg`.
- **Вариант Б (валидный JSON-массив, элемент без поля `items`)** — **не
  закрыт**. `parseOrders()` проверяет только форму верхнего уровня
  (`Array.isArray`), но не структуру каждого элемента массива;
  `orderItemsHtml` в `app.js` по-прежнему безусловно вызывает
  `.map` на `order.items`. Повторил тот же repro, что и в исходном
  баг-репорте — экран «Мои заказы» снова не открывается, консоль
  показывает тот же `TypeError: Cannot read properties of undefined
  (reading 'map')` в `orderItemsHtml`. Доказательство:
  `screenshots/retest-bug2-variantB-still-crashes.jpg`.

Баг 2 остаётся **открытым** как баг-репорт в целом, пока не закрыт
вариант Б — заголовок и шаги воспроизведения выше не меняю, чтобы не
терять историю; статус по каждому варианту зафиксирован здесь отдельно.

### Баг 5 (зависшие тексты ошибок) — статус: **не закрыт** (не входил в заявленные три)

Не был в списке из трёх заявленных исправлений, но пункт 2 упоминал
«тексты ошибок... сбрасываются», поэтому перепроверил отдельно.
`resetCheckoutForm()` вызывается только на успешном пути
`handleCheckoutSubmit` — при сценарии без успешной отправки (ошибка →
«Назад в меню» без исправлений → снова открыть оформление, тот же
непустой корзина) ничего не очищает текст ошибок. Повторил исходный
repro — «Введите имя» / «Введите адрес доставки» / «Введите корректный
телефон» снова видны на свежем визите без новой попытки отправки.
Доказательство: `screenshots/retest-bug5-still-stale-errors.jpg`.
