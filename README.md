# Кухня у Дома — QA-сессия (Задание 4)

Итоговый отчёт по домашнему заданию курса (Занятие 1, направление
QA). Готовый прототип сервиса доставки еды прогнан через
дисциплинированный QA-цикл: контекст → спецификация → тест-план →
проверка → баг-репорты → независимый аудит. Ход работы, промпты и
решения — в `sessions/`; этот файл — краткий свод результата.

## Запуск

```bash
# установка зависимостей
# нет — проект без npm и без сборки

# запуск приложения
python3 -m http.server 8765
# открыть http://localhost:8765/ — другой порт/адрес не используется

# автотест логики
node app.logic.test.mjs
# ожидаемый вывод: OK: all logic checks passed
```

Requirements: Python 3 (только для локального сервера) и Node.js
(только для `app.logic.test.mjs`) — оба не входят в рантайм самого
приложения, оно чистый `HTML/CSS/vanilla JS`.

## Что это за проект

Фронтенд-прототип без бэкенда: меню одного ресторана → корзина →
оформление заказа → подтверждение → история заказов (хранится в
`localStorage`). Приложение было собрано в отдельной, уже закрытой
сессии разработки — по сценарию Задания 4 QA-агент к моменту начала
работы получает готовое приложение и историю его создания не видит.
Мою роль в этом проекте описывает `AGENTS.md`: тестировщик, который не
пишет и не правит код приложения ни при каких обстоятельствах.

## Найденные баги

Полные баг-репорты с шагами воспроизведения и доказательствами —
`bug-reports.md`. Скриншоты — `screenshots/`.

| № | Заголовок | Severity | Зона | Статус после фикса (сессия 6) |
|---|---|---|---|---|
| 1 | Поле «Имя» не экранируется — HTML/JS-инъекция на экране подтверждения | Критично | Валидация формы | **Закрыт** |
| 2 | Некорректные данные в `localStorage["orders"]` роняют переход на «Мои заказы» необработанным исключением | Критично | История заказов | Открыт частично — невалидный JSON чинится, валидный массив с заказом без поля `items` всё ещё падает |
| 3 | Отправка формы с опустошённой корзиной молча возвращает в меню без сообщения | Не критично | Валидация формы | Открыт (не заявлен к фиксу) |
| 4 | Данные формы (имя/адрес/телефон) не очищаются между визитами — риск отправить заказ со старыми чужими данными | Критично | Валидация формы | **Закрыт** |
| 5 | Тексты ошибок валидации виснут на экране без новой попытки отправки | Не критично | Валидация формы | Открыт — фикс сбрасывает ошибки только на успешном пути отправки |

Баги 1–3 найдены при выполнении исходного тест-плана. Баги 4 и 5 —
при перепроверке находок независимого аудита (баг 4 подтверждён не
только по шагам, но и «на живом тестировщике»: при ручной проверке я
дважды подряд случайно отправил реальные заказы со старыми данными —
это зафиксировано в самом баг-репорте как часть доказательства, а не
скрыто).

**Повторная проверка после фикса (сессия 6).** Код обновили вне
QA-роли, заявив три исправления. Перепроверил тем же способом — живым
воспроизведением, не на слово: 2 из 3 закрыты полностью (Баг 1, Баг 4),
1 закрыт лишь частично (Баг 2 — только вариант с невалидным JSON,
вариант с валидным массивом без поля `items` у заказа по-прежнему
роняет экран необработанным исключением). Регрессий не найдено. Полная
таблица и доказательства — раздел «Повторная проверка после фикса» в
`bug-reports.md`. Первая попытка перепроверки Бага 1 дала
ложноотрицательный результат из-за HTTP-кэша браузера со старой версией
`app.js` — исправлено жёсткой перезагрузкой, подробности в
`sessions/session-6.md`.

## Сравнение: наивный прогон vs прогон по спецификации

Помимо QA-сессии по спеке, для этого же приложения существует
независимый наивный прогон — чисто исследовательское тестирование без
плана и чек-листов (`sessions/session_native.md`). Полное сравнение по
4 пунктам (что нашли одинаково, что нашёл только один из прогонов и
почему, разница в форме результата, измеримый вывод) — в
`comparison.md`. Коротко:

- Между двумя прогонами вместе — **7** уникальных багов. Наивный нашёл
  **4** (57% от объединённого множества), прогон по спеке — **5**
  (71%). Ни один прогон поодиночке не нашёл всех семи.
- **2 бага общие** — независимо найдены обоими: XSS-инъекция через
  поле «Имя» (совпадает полностью, включая способ доказательства), и
  персистентность старых данных формы между заказами (тот же
  механизм, но разная итоговая severity — наивный прогон оценил это
  как некритично, я — как критично, после того как при живой проверке
  дважды случайно отправил реальные заказы со старыми данными).
- **3 бага нашла только спека** — падение экрана «Мои заказы» на
  испорченном `localStorage` (наивный прогон сознательно пропустил это
  как «маловероятный путь пользователя», а спека прямо указала копать
  в эту зону), молчаливый редирект при опустошении корзины прямо с
  экрана оформления (конкретная межэкранная комбинация, найденная
  через письменный чек-лист, а не случайным кликом), и зависшие тексты
  ошибок валидации (найдены только вторым, независимым проходом —
  аудитом).
- **2 бага нашёл только наивный прогон** — нестрогая валидация
  телефона (мусорная строка с ≥5 цифрами проходит) и отсутствие
  оверлея/тап-вовне у панели корзины на мобильном. Первый я сам же
  заметил в черновом чек-листе зоны 1 ещё в сессии 1, но не довёл до
  пункта тест-плана — честно зафиксировано в `comparison.md` как
  собственный процессный промах, а не как ограничение метода.

Отдельно перепроверено по прямому запросу (сессия 5): наивный прогон
сообщает об успешном resize окна до 390×844, тогда как в моей сессии 1
тот же инструмент стабильно давал `window.innerWidth = 606`. Повторная
проверка на 4 свежих вкладках с одинаковым запросом 375×700 дала 4
разных результата (без эффекта, 606×457, 1000×657, 606×557), и после
первого успешного ресайза конкретной вкладки повторные вызовы на ней —
молчаливый no-op. Вывод: `resize_window` в этой среде недетерминирован
сам по себе, 606px не был устойчивым минимумом — подробности в
`comparison.md` и `sessions/session-5.md`.

## Что не сделано / сознательно упрощено

- **Полное закрытие всех багов** — не достигнуто, и не должно было быть
  целью QA-роли. Правка кода приложения самим QA-агентом запрещена
  `AGENTS.md` на всём протяжении проекта — все правки в сессии 6 внёс
  кто-то другой, я их только проверял. Из 5 багов на конец проекта
  закрыто 2 (XSS, старые данные формы), 1 закрыт частично (падение на
  `localStorage` — только вариант с невалидным JSON), 2 остаются
  открытыми (молчаливый редирект при пустой корзине, зависшие тексты
  ошибок валидации). Критерий приёмки «повторная проверка после фикса»
  при этом выполнен — сама повторная проверка состоялась и дала честный,
  не подогнанный результат (раздел выше, `bug-reports.md`).
- **Кроссбраузерность** — тестировалось только в Chrome через
  `claude-in-chrome`. Второй браузерный движок (Safari/Firefox) не
  проверялся — в сессии не было для него автоматизации, а
  устанавливать новый инструмент (например, Playwright MCP) без
  отдельного вопроса запрещено правилами проекта. Обозначено как
  задел на будущее.
- **Accessibility** (клавиатурная навигация, видимость фокуса) —
  сознательно вне рамок этой сессии: не требовалось заданием, не
  укладывается в выбранную таксономию кластеров багов, отдельный
  QA-раунд на будущее.
- **Мобильная ширина 375px** — проверена не полностью. `resize_window`
  в `claude-in-chrome` в этой среде недетерминирован (перепроверено на
  4 вкладках в сессии 5 — 4 разных фактических результата на
  одинаковый запрос, ни разу не 375), а не имеет фиксированный минимум
  в 606px, как было написано изначально. Испробован обходной путь
  через CSS `zoom` — не сработал, медиа-запросы Chrome считаются
  от физического viewport, а не от CSS-зума. Реально подтверждено:
  768px и ~606px — вживую скриншотами на всех 5 экранах; поведение
  <420px — только чтением синтаксически верного CSS-правила в
  `style.css`, без подтверждения фактического рендера. Граница честно
  зафиксирована в `qa-notes.md`, а не выдана за «пройдено».
- **Полный перебор позиций меню** — ни в спека-прогоне, ни в наивном
  не тестировались все 9 SKU по отдельности (см. `comparison.md`) —
  оба ограничились выборкой/механикой корзины, а не перечислением.

## Допущения и ограничения

- Тестовые данные — реалистичные российские (имя, адрес, телефон), без
  проработки персоны или демографии продукта.
- `localStorage` браузера доступен и не ограничен приватным/инкогнито-
  режимом на машине тестировщика.
- Системные часы машины тестировщика не менялись ни разу — там, где
  нужно было проверить конкретное время (границы получаса, переход
  через полночь), использовался прямой вызов `generateDeliverySlots` с
  явно заданным `Date`, а не смена системных часов ОС (это запрещённое
  действие).
- Сервер запускается строго `python3 -m http.server 8765`, приложение
  живёт только на `http://localhost:8765/`.
- Версия Chrome, использованная в тестировании, — 151.0.0.0 (macOS,
  Darwin 25.5.0), зафиксирована в окружении каждого баг-репорта.
- Полный список открытых вопросов (пробелы вокруг полей, повторная
  отправка формы, часы работы заведения, политика экранирования) — в
  `qa-notes.md`, каждый — с явной отметкой, зафиксирован ли по нему уже
  факт поведения или нет.

## Независимый аудит

Проведён отдельным `general-purpose`-агентом без контекста QA-сессии —
только самодостаточный бриф и код проекта. Аудит независимо
переисполнил (не просто прочитал) два критичных бага и получил
идентичные посимвольно консольные трассировки, нашёл фактическую
неточность в одном баг-репорте, один пропуск покрытия относительно
спеки и один новый баг. Полный текст отчёта аудитора и разбор по
каждой находке — `sessions/session-2.md`. Ни с одной находкой аудита
не спорили по существу — разногласия были только по формулировке и
группировке.

## Честно: чего в этом отчёте не было

Отчёт с идеально гладким ходом работы выглядел бы придуманным. Что
реально было: неверно понятая последовательность шагов на этапе
спецификации (написал чек-листы до того, как их попросили, пришлось
откатиться к вопросам); передумывание пользователя по выбору
браузерного окружения прямо в диалоге; техническое ограничение среды,
не позволившее закрыть один пункт тест-плана честно на заявленной
ширине; собственная ошибка при автоматизации, которая случайно
отправила два реальных заказа со старыми данными — и именно она стала
лучшим доказательством одного из багов; при сравнении с наивным
прогоном обнаружился собственный процессный промах (баг с телефоном
был замечен в черновом чек-листе ещё в сессии 1, но не доведён до
тест-плана); расхождение среды по `resize_window` перепроверено и
объяснено в сессии 5 (инструмент недетерминирован, не имеет
фиксированного минимума); в сессии 6 первая попытка перепроверить фикс
XSS дала ложноотрицательный результат из-за HTTP-кэша браузера со
старой версией кода — заметил это только потому, что сверил через
`curl`, что сервер уже отдаёт исправленный файл, прежде чем записывать
баг как неисправленный. Все эти моменты зафиксированы в
`sessions/session-1.md` — `session-6.md` как есть, без приглаживания.
