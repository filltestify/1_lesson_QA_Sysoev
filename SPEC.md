# Спецификация

## Что делаем

QA-сессия для готового веб-прототипа доставки еды («Кухня у Дома»):
фронтенд без бэкенда (HTML/CSS/vanilla JS), путь пользователя
меню → корзина → оформление заказа → подтверждение → история заказов,
состояние — `localStorage`. Приложение уже реализовано в закрытой
сессии разработки; в этой сессии код не пишется и не правится —
только тестируется. Глубокое системное тестирование с перевесом на
1–2 зоны риска (по итогам чек-листов), а не поверхностный охват всего
сразу.

## Для кого и зачем

Зачем — сдать QA-часть курса (Задание 4 из `homework.pdf`), показать
дисциплинированный цикл тестирования на чужом уже готовом прототипе
(сессия разработки закрыта, история создания недоступна).

Для кого — артефакт увидит проверяющий курса. Внутри сценариев
тестировщик представляет обычного человека, заказывающего еду:
тестовые данные (имя, адрес, телефон) реалистичные и российские ровно
настолько, чтобы выглядеть правдоподобно — без отдельной персоны или
демографии продукта.

## Сценарии

Тестирование сосредоточено на 4 функциональных зонах риска, выявленных
при чтении кода (полные чек-листы граничных и негативных случаев по
каждой зоне зафиксированы в журнале сессии, лягут в основу тест-плана):

1. **Валидация формы оформления заказа** — имя, адрес, телефон,
   повторная отправка, инъекции в незаэкранированный вывод на экране
   подтверждения.
2. **Количество и удаление позиций в корзине** — в т.ч. отсутствие
   персистентности корзины между перезагрузками страницы.
3. **Генерация слотов доставки** — округление времени, границы
   получаса, переход через полночь.
4. **История заказов через `localStorage`** — отсутствующий, пустой,
   испорченный, структурно некорректный JSON. Отдельно верифицируется
   (не как открытый вопрос, а как факт поведения): порядок отображения
   при совпадающем `timestamp` двух заказов детерминирован —
   `renderHistory` не сортирует по времени, а разворачивает массив
   через `.slice().reverse()`, то есть выдаёт обратный порядок
   добавления.

Отдельно, вне 4 зон: инъекции/XSS через поля формы — включены как
отдельный пункт тест-плана (обнаружено при чтении кода).

Окружение прогона: Chrome через `claude-in-chrome`, три ширины окна —
обычная desktop, 768px (планшет), 375px (мобильная); на 768/375
отдельно проверяем, не ломается ли вёрстка, и при обнаружении поломки
уточняем границу соседними значениями ширины. Второй браузерный движок
(Safari/Firefox) — вне рамок этой сессии.

Финальный тест-план (8–12 пунктов) собирается отдельным шагом после
подтверждения этой спецификации, с перевесом на зоны, где чек-лист
показал больше всего пограничных случаев, но не в ущерб
зонам-аутсайдерам (см. критерии приёмки).

## Состояния

- Корзина: пусто (0 позиций, кнопка «Оформить заказ» заблокирована) /
  есть позиции (счётчик и сумма актуальны) / только что опустошена
  вручную во время нахождения на экране оформления.
- Форма оформления: не заполнена / заполнена корректно / заполнена с
  ошибками (по каждому полю отдельно) / отправлена повторно.
- История заказов: нет заказов («Заказов пока нет.») / есть один или
  несколько заказов / `localStorage` испорчен или содержит структурно
  некорректные данные (нештатное состояние, ожидаемое поведение не
  задано — см. открытые вопросы).
- Слоты доставки: обычное время суток / ровно на получасовой границе /
  около полуночи (переход через сутки).
- Вёрстка: обычная desktop-ширина / 768px / 375px — на каждой все
  элементы видимы, не наезжают, без горизонтальной прокрутки
  (проверяем, но без формального SLA на адаптив — в задании его нет).

## Чего точно не делаем

- Не редактируем и не «чиним» код проекта ни при каких
  обстоятельствах — уже закреплено в `AGENTS.md`, дублируется здесь
  для полноты.
- Не тестируем в другом браузерном движке (Safari/Firefox) — нет
  настроенного инструмента в этой сессии; кандидат на будущий раунд с
  Playwright MCP.
- Не тестируем accessibility (клавиатурная навигация, видимость
  фокуса, Enter/Space) — сквозное измерение поверх выбранных 4 зон, в
  задании не требуется, чистого кластера под неё в таксономии багов
  нет. Кандидат на отдельный QA-раунд в будущем.
- Не устанавливаем новые инструменты (Playwright MCP и т.п.) без
  отдельного вопроса — уже закреплено в `AGENTS.md`.
- Не нагружаем приложение искусственно (сотни заказов, стресс-тест
  `localStorage`/квоты) — не входит в объём этой сессии.
- Не проверяем реальную оплату — приложение не интегрировано с
  платёжным провайдером (способ оплаты — просто поле формы).

## Допущения

- Тестовые данные — реалистичные российские (имя, адрес, телефон), без
  проработки персоны или демографии продукта.
- `localStorage` браузера доступен и не ограничен приватным/инкогнито-
  режимом на машине тестировщика.
- Системные часы машины тестировщика корректны (важно для зоны
  «слоты доставки»).
- Сервер поднят строго командой из `AGENTS.md`
  (`python3 -m http.server 8765`), приложение открывается только по
  `http://localhost:8765/`.
- Версия Chrome — та, что установлена и доступна через
  `claude-in-chrome` на момент тестирования; конкретная версия
  фиксируется в окружении каждого баг-репорта.

## Открытые вопросы

Ожидаемое поведение нигде не задано — фиксируются как список, не как
дефекты, трактовку не выбираем сами:

1. Пробелы по краям поля (имя/адрес) — обрезаются ли перед
   сохранением/показом, или сохраняются как есть?
2. Что должно происходить при испорченном/структурно некорректном
   `localStorage` (сейчас, по коду, — необработанное исключение при
   переходе на экран истории)?
3. Повторная отправка формы оформления (два быстрых клика по
   «Подтвердить заказ») — создание дублирующего заказа: ожидаемое
   поведение — разрешить, блокировать повторный клик, или считать
   идемпотентным?
4. Персистентность корзины между перезагрузками страницы — должна
   сохраняться (как история заказов) или намеренно эфемерна?
5. Слоты доставки генерируются круглосуточно без учёта часов работы
   заведения — это осознанное решение или недосмотр?
6. Политика экранирования пользовательского ввода (имя/адрес/телефон/
   комментарий) в `innerHTML` на экране подтверждения — нигде не
   описана; включаем как тест-кейс на инъекцию (см. «Сценарии»), но
   сама ожидаемая политика не задана.
